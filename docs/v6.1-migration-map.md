# V6.1 → Supabase data migration map

## Source format

V6.1 saves its browser state under:

\`\`\`js
localStorage.getItem("productionManagementV4")
\`\`\`

The saved object contains \`brandProducts\` and \`plans\`. Each plan contains hourly \`hourTargets\` and an \`entries\` object keyed by hour index. An entry contains \`actual\`, \`rejected\`, serial start/end, rejection reason, remarks and (for V6.1) per-unit \`reworkItems\`.

## Export from each browser

Open the V6.1 application on the device/browser that contains the records, open DevTools → Console, and run:

\`\`\`js
const saved = localStorage.getItem("productionManagementV4");
if (!saved) throw new Error("No saved V6.1 data was found in this browser");
const blob = new Blob([saved], { type: "application/json" });
const link = document.createElement("a");
link.href = URL.createObjectURL(blob);
link.download = "productionManagementV4-export.json";
link.click();
URL.revokeObjectURL(link.href);
\`\`\`

Repeat for every device/browser that contains records. Keep each export unchanged as a source backup. Do not upload browser exports into this repository because they may contain employee names, serials or operational data.

## Normalization mapping

| V6.1 field | Supabase target |
|---|---|
| \`brandProducts[brand]\` | \`pm_brands\` |
| \`brandProducts[brand][product]\` | \`pm_products\` linked to brand |
| model array under a product | \`pm_models\` linked to product |
| \`plan.id\` | \`pm_production_plans.legacy_id\` (string form) |
| \`plan.date\` | \`pm_production_plans.plan_date\` |
| \`plan.shift\`, \`plan.line\` | matching plan columns |
| \`plan.brand/product/model\` | resolve to brand/product/model UUIDs |
| \`plan.qty\` | \`pm_production_plans.planned_qty\` |
| \`plan.status\` | lowercase \`draft/published/completed\` |
| \`plan.hourTargets[i]\` | \`pm_plan_hour_targets\` row with \`hour_index=i\` |
| \`plan.entries[i].actual\` | \`pm_hourly_production.actual_qty\` |
| \`plan.entries[i].rejected\` | \`pm_hourly_production.rejected_qty\` |
| \`startSerial/endSerial/reason/remarks\` | matching hourly production columns |
| each rejected unit in \`reworkItems\` | \`pm_rework_units\` row for that hourly entry |

## Important preservation rules

1. **Do not add rejected quantity to actual quantity.** V6.1 actual already includes rejected units. Accepted is \`actual_qty - rejected_qty\`.
2. Insert a plan and all eight target rows before inserting its hourly records.
3. Inserting an hourly row automatically creates one pending \`pm_rework_units\` row for each rejected unit. Then reconcile each generated unit with the V6.1 unit's \`unitNumber\`, serial, original reason, status and resolution remark.
4. Map V6.1 \`Pending\` → \`pending\`, \`Completed\` → \`completed\`, and \`Finally Rejected\` → \`finally_rejected\`.
5. Resolved V6.1 units require a non-empty resolution remark. Resolve those rows using a trusted migration process after the generated pending rows exist.
6. Never reduce a stored rejected quantity below the number of already resolved rejection units. The database trigger blocks that operation.
7. The source HTML may initialize demonstration plans when no saved browser data exists. Confirm each plan is real before importing it.
8. Keep the original V6.1 JSON exports read-only until reconciliation and report totals have been signed off.

## Serial-number caveat

V6.1 stores an hourly serial start/end range. That range is retained on the hourly row. It does not necessarily identify the exact serial number belonging to each rejected unit. Only populate \`pm_rework_units.serial_number\` when the unit-level serial is known; otherwise preserve the unit number and original range rather than inventing a serial.
